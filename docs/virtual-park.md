# Virtual process park

Run from the repository root after building `bin/niceproxy` and `web/dist`:

```sh
python3 scripts/virtual-park.py \
  --caddy /tmp/niceproxy-tools/caddy \
  --output test-results/virtual-park-default.json
```

The harness requires Linux, Python 3.9+ and Caddy **2.10.2**, with no Python dependencies. Defaults are three instances, 64 simultaneous TCP clients per instance, and 20 retarget cycles. `--binary` defaults to `bin/niceproxy`; `--instances`, `--clients`, `--cycles`, `--output`, and `--work-dir` are configurable. `--functional-only` runs only startup plus routing/isolation/concurrent clients and labels the JSON suite accordingly. `--quick` reduces client and cycle counts but retains real UDP expiry checks. The work directory must not already exist. Run artifacts belong under ignored `test-results/`; the default creates a unique directory there. Ports are allocated from the OS ephemeral range, so an unrelated concurrent binder can cause a reported failure rather than silent retries that hide a listener bug.

This is a **process topology**, not VMs or containers. Every tenant has a distinct `127.77.x.y` address, a niceproxy process, its bundled Caddy child, two asyncio backend subprocesses, separate data/runtime directories, and distinct ports. The parent runs real TCP/UDP/HTTP clients, with bounded parallel TCP workers. All tenants retain their requested TCP clients concurrently before exchanging payloads, so the report distinguishes per-instance and aggregate concurrency. Caddy public listeners bind wildcard addresses on distinct ports, as the product currently specifies; direct and panel listeners bind tenant IPs. No NAS, existing demo, credentials, remote service, Docker socket, privileged operation, host firewall, or network namespace is used. Internal TLS verifies the instance's CA and DNS hostname without modifying the host trust store. A temporary short `/tmp/np-park-*` symlink points into the artifact directory to stay within Linux's Unix-socket path limit.

Scenarios cover:

- HTTP host/path matching and stripping, rejection of foreign-tenant and unknown Host on HTTP and HTTPS with a verified current SNI; path boundary rejection; internal HTTPS CA and hostname verification; backend identities and unpredictable TCP/UDP payloads across tenants.
- Server-first TCP, idle clients without client payload, simultaneous clients, half-close EOF, hot retarget while an old stream and continuously reconnecting clients remain active. New streams verify the selected target; old streams continue exchanging nonces.
- Logical conflicts returning 409 without changing revision. An externally occupied port must report partial apply with `appliedRevision: -1`, retain the authenticated panel, and recover after reconcile.
- Both explicit HTTP port ownership directions, direct Retire, and a held direct stream checked after every relevant transition. Continuous new connections are classified as Caddy, direct, or failures. JSON includes mutation start/end times and individual probe timestamps. The recorded failure interval **includes the user operation gaps between multiple API mutations**, with no artificial pause between API mutations by default. `--handover-pause-ms` can add an explicit observation delay; that value is recorded in the report. A brief pause after a live direct listener is established lets the probe observe that stable stage. It is a sampled interval, not an exact outage measurement or zero-loss assertion. The held stream is a direct TCP stream, not a Caddy HTTP keepalive or websocket preservation claim.
- Backend SIGKILL/restart, niceproxy SIGKILL, Caddy parent-death cleanup (including children spawned by non-leader Go threads), stale control socket replacement, and restart using the same DB/runtime/session/revision.
- TCP and UDP admission saturation, reject counters, per-rule active/accepted/closed counters, and UDP association expiry. The product's default 60-second UDP timeout is respected; association retention before expiry is not treated as a leak.
- `/proc` FD, RSS and thread samples for niceproxy and Caddy during churn and after idle. Post-warmup niceproxy churn samples permit 32 MiB RSS, 32 FD and 16 thread growth. These generous bounds detect gross growth during this finite run; they do not establish long-term leak freedom or exact memory stability. Idle checks require active zero and accepted equal closed, report the final counters for each TCP/UDP rule, and apply the same RSS/FD/thread growth tolerances to each process with a same-PID baseline. Idle processes also have absolute caps of 128 threads and `4 × clients + 512` FDs. Restart resets process-local statistics honestly.

The total run has a 175-second watchdog. Arguments are capped at eight instances, 128 clients, and 50 cycles. TCP reads loop until the expected byte count; no assumption is made about `recv()` chunk boundaries. Backend concurrency uses one asyncio loop per subprocess rather than a thread per connection. Every subprocess gets a separate session; cleanup signals entire groups, even when niceproxy already exited, so surviving Caddy children are covered. Failure, SIGINT, SIGTERM and timeout produce a nonzero exit and preserve logs plus JSON. As with any userspace program, SIGKILL of the harness itself cannot execute cleanup.

The JSON report records parameters, topology PIDs and ports, per-scenario pass/fail and duration, ownership samples, admission counters, resource measurements, and any failure traceback. Backend and proxy logs, private temporary databases/CA data and `summary.txt` remain in the private artifact directory; they contain only generated test state. Session cookies and generated passwords are not printed in reports. The harness does not benchmark throughput or compare proxy products. Full Go race/vet, frontend checks and Linux splice `strace` verification remain separate parent-task checks.
